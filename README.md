## 🧭 Overview

Universities juggle hundreds of shared resources across many buildings and departments. Double bookings, lost approval emails, and no record of who used what are common problems.

The **Campus Resource Management System** fixes this with one platform where:

- **Students & Faculty** search for resources, check availability, and request bookings.
- **HODs & Admins** approve or reject requests and manage the campus setup.
- **Lab Assistants** log maintenance and keep resource status up to date.
- **The database itself** enforces the rules through constraints, triggers, views, and stored procedures.

## ✨ Features

| Module | What it does |
|---|---|
| 🔐 **Authentication** | JWT-based login, protected routes, bcrypt password hashing |
| 📊 **Dashboard** | Live stats: total bookings, available resources, pending approvals, active users, and booking breakdowns |
| 🧱 **Resources** | Browse and filter by category, building, capacity, features, and status |
| 📅 **Bookings** | Request bookings with automatic overlap and conflict detection |
| ✅ **Approvals** | Approval workflow for HODs and Admins, with remarks |
| ⏳ **Waitlist** | Join a queue when a resource is already booked |
| 🔧 **Maintenance** | Report issues with priority levels; critical issues take the resource offline automatically |
| 🔔 **Notifications** | Booking status alerts generated by DB triggers, plus an unread badge |
| 🕒 **Usage Logs** | Check-in / check-out tracking of actual resource usage |
| 🧾 **Audit Logs** | Full trail of inserts, updates, and deletes with old/new values |
| ⚙️ **Admin Panel** | Manage users, buildings, departments, time slots, academic terms, holidays, and resource policies |

## 🗄 Database Design

The schema (`campus_resource_schema.sql`) is normalized and contains **21 tables**, **3 views**, **3 triggers**, and **2 stored procedures**.

<details>
<summary><b>📋 Tables (21)</b></summary>

| Group | Tables |
|---|---|
| Organization | `Building`, `Department`, `Role`, `User` |
| Resources | `Resource_Category`, `Resource`, `Resource_Feature`, `Resource_Feature_Map`, `Resource_Policy`, `Department_Resource_Access` |
| Scheduling | `Time_Slot`, `Academic_Term`, `Holiday_Calendar` |
| Bookings | `Booking`, `Recurring_Pattern`, `Approval`, `Waitlist` |
| Operations | `Maintenance_Log`, `Usage_Log`, `Notification`, `Audit_Log` |

</details>

<details>
<summary><b>👁 Views</b></summary>

- `vw_active_bookings`: pending and approved bookings joined with user, department, resource, and building details
- `vw_resource_availability`: every resource with its status, capacity, and count of upcoming approved bookings
- `vw_dept_booking_stats`: total, approved, rejected, and pending bookings per department

</details>

<details>
<summary><b>⚡ Triggers</b></summary>

- `trg_booking_status_notification`: notifies the user automatically when a booking's status changes
- `trg_maintenance_resource_status`: sets a resource to *Under Maintenance* when a **Critical** issue is logged
- `trg_audit_booking_insert`: writes an audit entry for every new booking

</details>

<details>
<summary><b>🧩 Stored Procedures</b></summary>

- `sp_check_availability(resource, date, start, end)`: checks for conflicting pending/approved bookings in a time range
- `sp_user_booking_history(user)`: returns a user's complete booking history

</details>

## 🚀 Getting Started

### Prerequisites

- [Node.js](https://nodejs.org/) 18 or newer
- [MySQL](https://dev.mysql.com/downloads/) 8.x
- Git

### 1. Clone the repository

```bash
git clone https://github.com/Nishu-28/campus-resource-management.git
cd campus-resource-management
```

### 2. Set up the database

```bash
mysql -u root -p < campus_resource_schema.sql
```

This creates the `campus_resource_db` database with all tables, seed data, views, triggers, and procedures.

### 3. Configure and run the backend

```bash
cd server
cp .env.example .env        # then edit DATABASE_URL and JWT_SECRET
npm install
npx prisma generate
npm run dev                 # API runs on http://localhost:5000
```

### 4. Run the frontend

```bash
cd ../client
npm install
npm run dev                 # App runs on http://localhost:3000
```

Vite proxies `/api` requests to `http://localhost:5000`, so no extra CORS setup is needed in development.

## 🔌 API Reference

All routes are prefixed with `/api`. Every route except `/auth` and `/health` needs an `Authorization: Bearer <token>` header.

| Endpoint | Description |
|---|---|
| `POST /auth/login` | Log in and receive a JWT |
| `GET /health` | Health check |
| `/dashboard` | Summary statistics |
| `/resources` | Resource CRUD and filtering |
| `/bookings` | Create, list, and cancel bookings |
| `/approvals` | Approve or reject bookings |
| `/waitlist` | Waitlist entries |
| `/maintenance` | Maintenance logs |
| `/notifications` | User notifications |
| `/usage-logs` | Check-in / check-out logs |
| `/users`, `/roles`, `/departments`, `/buildings` | Organization management |
| `/time-slots`, `/academic-terms`, `/holidays` | Scheduling configuration |
| `/resource-policies` | Booking rules per resource category |
| `/audit-logs` | System audit trail |
